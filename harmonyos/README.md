# Showly HarmonyOS Preview v0.9.0

Unofficial native ArkTS prototype, not a complete Showly port. Your app uses Trakt but is not endorsed or certified by Trakt.

## Personal BYOK configuration

The HAP contains no developer Client ID or secret. No GitHub Actions credential is required.
1. Open https://developer.trakt.tv/apps in the system browser and connect a verified GitHub account.
2. Create a personal Development app (Standard). Use the actual project description and register exactly `showlyharmony://trakt` for development testing. Follow Trakt's terms and branding requirements. This is for personal use, not rate-limit evasion.
3. Paste the Client ID into the app. The app validates it using one read-only Standard API request, persists it in Preferences, and optionally starts PKCE authorization. No Client Secret is requested.
4. Sign in at Trakt. The app checks state and PKCE; it stores the refresh token using HarmonyOS Asset Store, with local-only synchronization and device-unlocked access. Access tokens are in memory. On restart or foreground after expiration the app attempts renewal; retry is available. Rotated refresh tokens replace the previous token. If secure storage fails or token exceeds its 1024-byte limit, login may need repeating; no plaintext fallback.
5. Change or clear credentials via settings. Switching first clears the old local authorization; local watch records are preserved. Local logout does not revoke remote grants. Use Trakt website to revoke.

Production integration requires Trakt approval and HTTPS verified app links; this development custom scheme is not production-ready. App creation is manual on the official website: no scraping, cookie access or automated account registration.
Privacy: credentials and watch records stay on device except the HTTPS requests to Trakt needed to validate, search and authorize. No analytics. Explicitly confirmed or opted-in episode history writes are supported by later versions below. User-initiated authenticated cloud preview and explicit additive local import are supported.

## Test checklist

- First launch without ID: local library works, login disabled, guide opens.
- Invalid ID or offline validation does not replace existing configuration.
- Valid ID saves across restart; search and PKCE login require live verification.
- Successful login, restart, refresh, cancellation, logout, change ID, and expired grant must be tested on device.
- Upgrade from v0.3.0 preserves the unchanged local library schema.
- CI builds unsigned preview HAP only; no device runtime tests in CI.

## Read-only Trakt library preview / import

The user explicitly requests a cloud read. GET /sync/last_activities brackets the four paginated datasets (watched movies, watched shows with extended=progress, movie and show watchlists). Pagination uses returned page and item counts; incomplete or duplicate results abort without changes. Changed activity revision aborts the snapshot. Session generation is checked on every page and before import. HTTP 429 or other failures stop without retries. Cloud preview is in memory and cleared on account change or disconnect.
The user may import only new watchlist titles and watched movies; existing local records take precedence. If a movie appears in both cloud lists, watched wins for a new local title. Watched shows are shown as counts of unique episodes with positive plays, not marked completed. No cloud episode data is persisted or written back. Season zero is counted if supplied by Trakt. Local schema stays v1; Preferences size limits still apply. Very large imports may require a future relational store.
Refs: https://developer.trakt.tv/docs/pagination ; https://github.com/trakt/trakt-api/discussions/775 ; https://developer.trakt.tv/docs/api-use-policy .
Device test: verify multi-page lists, no duplicates, correct partial-show counts, invalid/expired authorization, rate limiting, offline requests, account switch, repeated import (zero new records), and preservation of existing local entries. CI does not validate live account behavior.

## v0.6.1 artwork diagnostics

The app distinguishes absent API artwork, rejected URL shape, DNS/connect/timeout, CDN HTTP status, invalid binary/WebP signature, cache write and ArkUI image rendering failures. Select the first eligible URL in the API poster array; permit variable artwork size path segments while retaining strict HTTPS Trakt host and media-path checks. ## v0.7.3 local episode journal

New independent SQLite-backed RelationalStore database showly_episodes.db. Existing Preferences library, account, and appearance stores remain authoritative and unchanged; migration of old titles into RDB is deliberately deferred, avoiding a destructive or dual-write migration. Public Trakt seasons?extended=full,episodes provides the catalog; only episodes with confirmed past air dates and positive ordinary season/episode/Trakt IDs are eligible. Cache a catalog on explicit refresh, preserve prior data on failure. Local marks are separate from cloud watched status; the event log stores one atomic row per action (including season batch), ordered by an autoincrement sequence, with stable Trakt episode IDs and timestamp. Replay yields local state, progress and next earliest unwatched aired episode; no second mutable watched table and no partial season writes. Local actions do not imply whole-show watched, do not use OAuth and are not queued for automatic upload to any account. Cloud progress still read-only. Recent 12 locally modified shows accessible offline from progress tab; old local library and all previous tabs unchanged. Future cloud reconciliation requires explicit account binding and conflict policy. 
Device tests: catalog download, mark one and undo, confirm season batch and undo, kill/relaunch offline, next episode and totals, verify original library and Trakt remain unchanged, offline without cached catalog, future episodes and specials excluded.

## v0.8.2 manual single-episode history addition
Only explicit local watched additions from a verified preview may be selected, one at a time. The confirmation names the episode and uses the confirmation timestamp as watched_at. Existing explicit pre-binding journal entries require the same manual confirmation. Fresh account UUID, binding, full paginated snapshot, targeted history read and activity checks precede POST /sync/history (episodes only, stable Trakt ID); an existing cloud play is skipped. SQLite sync_upload_guard(account_uuid,episode_id) primary key is reserved before POST; even uncertain failures/crashes keep the guard and no automatic or manual resend is allowed for that ID in this version. Post-write targeted GET /sync/history/episodes/{id} and account verification confirm presence, not attribution of concurrent plays. A guard reserved but not sent may conservatively block the episode. Trakt history API is not idempotent; simultaneous writes from another device, or losing app data, can still produce duplicate plays. No cloud deletion, batch upload, automatic sync, cloud import of episode history, watch-time reconstruction, or guard reset. Trakt may automatically update related progress/watchlist on a new play. Existing schema preserved; new guard table only.

## v0.8.3 single-play removal with conservative conflict handling
New sync_play_receipt table only. For uploads from this version onward, save a candidate history receipt only after a successful added=1 response, exactly one readback play, matching episode ID, action=watch, safe integer history ID, and watched_at in the same minute as the explicit confirmation. Trakt has standardized watched_at to minute precision (announcement #694); timestamp alone cannot prove provenance. Concurrent changes between POST and readback cannot be ruled out, so user must review the specific time and ID before removal. Old v0.8.2 uploads have no receipt and remain ineligible; no retroactive attribution. Conflict rows with an available receipt allow manual selection and separate confirmation only. Fresh account UUID and binding, explicit latest local unwatch intent, matching exact history ID and time, one cloud play, and stable activity are required. Multiple plays, changed/missing metadata, unsafe int64 IDs, wrong account or uncertain receipts block removal. POST /sync/history/remove uses only {ids:[historyId]}, never media IDs. Reserve removal before sending and never retry automatically; targeted readback confirms absence only if the returned list is complete. Existing upload guard remains after removal (no re-add in this version). No bulk removal, full three-way synchronization, automatic conflict resolution, or reset of pending guards. No live account changes performed by CI/development.
References: https://trakt.docs.apiary.io/reference/sync ; https://github.com/trakt/trakt-api/discussions/694 ; https://github.com/jellyfin/jellyfin-plugin-trakt .
Device tests: new truly watched episode addition with receipt; locally unmark; conflict preview shows receipt; cancel then confirm only if the user really wants to remove that exact history; verify remote absence and unchanged unrelated plays. Legacy uploads, multi-play, wrong account and uncertain response must fail closed.

## v0.8.5.1 network recovery and read-only queue reconciliation
Use native NetworkKit default-network events (GET_NETWORK_INFO normal permission), page-show events and coalesced busy-gate completion. No background timer, no force network binding. Auto processing only starts while visible with the existing persisted opt-in, and checks visibility/account before POST. In-flight requests are not cancelled after submission. A previously guarded queue item is reconciled against a fresh activity-checked complete watched snapshot, and cleared only if the exact current event is present remotely. Absent guarded records remain protected: no guard reset, no automatic resend, no inferred removal receipt. Only unprotected explicitly authorized additions pass the existing batch upload gate. After a batch with newly protected unresolved entries, perform at most one further fresh read-only reconciliation per invocation, subject to visibility. Network recovery, auth readiness or manual processing can reconcile later. Diagnostics include phase, allowlisted validation error or numeric SDK/HTTP code, and post/readback outcome; never raw payloads/tokens. Logs refresh in finally and on open, distinguish guard vs catalog issue. Existing DB schema, consent, guard, receipts and records retained. No live account mutations in development. Device case: 18 previously guarded items later present remotely cleared by manual reconciliation; exact cause of the earlier incomplete write not proven. Test offline mark, reconnect in app, resume during auth, background/foreground, protected present and absent, lost response, unrelated record unchanged, permission fallback. Trakt rate limits apply; do not poll or blindly retry POST.

## v0.9.0 preview release and update checking

Builds of the independent harmonyos-bootstrap branch detect upstream master changes against the checked-in observation baseline (not a claim of complete port coverage). No merge, cherry-pick or rewrite of Android master. Source pushes trigger the existing pinned SDK build and artifact upload. A separate release job with contents:write/actions:read runs only for successful builds on the named fork/branch, verifies one HAP, checks build metadata, publishes a versionCode-qualified prerelease tag with an unsigned HAP, SHA256SUMS.txt and release-info.json. Draft remains unpublished if verification fails. Tags/releases are never overwritten; if a failed attempt leaves a draft, inspect it before retrying; increment versionCode for changes. GitHub artifacts remain a fallback. No signing key or Trakt API credentials in CI. No automatic installation; use the existing personal installation method, preserve data, verify SHA-256. Hash verifies integrity, not publisher signing identity.
Settings > Version & Updates > Check for updates reads public GitHub releases and upstream commit metadata without Trakt credentials. It compares numeric versionCode and ignores Android releases, drafts, and incomplete packages. No update download or background poll, no downgrade. A release with a valid published asset and digest is a preview, not a production signing or device-test claim.
GitHub schedule and workflow_dispatch require workflow availability on the default branch; master is intentionally untouched, so no independent periodic upstream monitoring or autonomous Android-to-ArkTS merge is enabled. Upstream detection runs on native pushes and user-initiated in-app checks. To enable independent scheduled detection, an explicit default-branch workflow or separate automation repository is needed.
References: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows ; https://cli.github.com/manual/gh_release_create ; https://docs.github.com/en/rest/releases/assets .
