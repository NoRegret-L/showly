# v0.9.3e.2c — startup and incremental read models
Android baseline e08cb90b: ProgressItemsCase / ProgressMoviesItemsCase use local data and Dispatchers.IO, local translation and artwork reads; MainActivity schedules WorkManager tasks separately. HarmonyOS uses native TaskPool (https://developer.huawei.com/consumer/en/doc/HarmonyOS-Guides/taskpool-introduction/) for pure episode resolution, sections and progress source. Serialized inputs/results only; a failed worker falls back to the same pure resolver. No database handles, tokens, authorization or sync writer on the worker.
- Cold start: open stores; one readiness-driven initial read. Once account UUID verified online, publish its cached observation without network catalog fill or checkpoint writes, then validate activity and reconcile through existing gates. Warm read reuses current snapshot; do not rewrite unchanged remote observation. Account verification, activity checks, read-only recovery and all POST/receipt guards remain unchanged.
- Whole read-model cache keyed by client, UUID, session generation, remote activity, local media records and episode-store read revision. Read revision increments on relevant episode mutations, including checkpoints, baseline, schedule and binding. Scope changes clear caches. Do not cache unresolved/missing/failed catalogs or pending new matches. Explicit refresh can bypass whole cache. Individual show computation reused only on exact serialized input equality and valid air-time interval; stale/missing metadata still eligible for original repair. New checkpoints may alter watchedAt and cause a necessary follow-up projection; unchanged matching checkpoints do not cause repeated projection. Private caches are process-memory only.
- No startup filesystem scan of all poster files: verify each visible card's poster once per process or explicit retry. Titles and season metadata still read at open for cached bilingual search. Publish current-page metadata in a batch, then optional off-page translations only for explicit search or title/user-rating sorting. Route changes cancel obsolete work at the next await. Use indexed title and episode lookups, revision-scoped memoization of collection/progress lists, actual broadcast/time-window/UTC-date expiry. Keep existing bounded pagination; LazyForEach migration deferred (requires List/Grid container and data source redesign: https://developer.huawei.com/consumer/en/doc/HarmonyOS-Guides/arkts-rendering-control-lazyforeach/).
- No new timers, heuristic refresh interval, external library or write permissions. Non-UI pure calculation runs on TaskPool when available; SQL and JSON preparation, initial metadata load, render and some catalog traversal remain on original paths. Missing catalogs still filled sequentially after cached display, not a background OS service. No offline cold-start UUID bypass. No changes to Trakt remote write implementation.
- Diagnostics: in app collection/advanced status, counts of whole projections/cache hits, per-show computed/reused counts, projection elapsed ms and first projection completion since component creation. Not a measurement of first interactive frame. Test fixtures use 393 synthetic shows: one full calculation, zero repeat calculations, one changed-show calculation; compare resolver output, checkpoint watchedAt, scope, data revision and air-time boundaries. CI compiles and runs pure fixtures; actual TaskPool behavior, cold-start first frame, memory and FPS require device profiling. Compare same-account cold/warm launches, no-change refresh, one episode mark, network recovery, logout/account switching, missing catalog, Chinese search and poster behavior, and sync receipt regression.
