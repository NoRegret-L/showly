# v0.9.3e.2c.1 — deep startup performance (0.9.3.16 / build 40)
Baseline: Android e08cb90b ProgressItemsCase and ProgressMoviesItemsCase use local DB and Dispatchers.IO; Build 39 uses in-process whole and per-show caches. Use native ArkData SQLite and ArkUI List/IDataSource/LazyForEach (https://developer.huawei.com/consumer/en/doc/harmonyos-guides/arkts-rendering-control-lazyforeach/). No third-party dependencies or heuristic refresh thresholds.
- Separate optional derived progress_projection_cache table in existing episode database. Schema-versioned account/client/local-binding scope; device cache isolated. Disk entries use the entire exact per-show input (catalog, remote plays, local ids, decisions, watch times, checkpoints, baseline) and actual air-time bounds, never a resettable process revision. No OAuth tokens, consent, receipts, or sync queue state serialized. No changes to existing table schemas, sync writers, POST/undo rules or backup format. Cache is dispensable; corrupt/mismatched/unavailable data recomputes from existing sources. Current UUID must be verified online before signed-in restore. Persist only complete eligible resolver outputs; strip checkpoint matches, bypass disk reuse when any local decision has no matching checkpoint. Existing live markNext validation remains required. Cross-process cache is per-show, not a materialized whole library: SQL scans, JSON key validation and some projection work still occur; disk space can grow with accounts, no eviction policy added.
- First cloud projection no longer performs network catalog repair. After verified observation and publication, foreground repair queue fetches public metadata without cloudBusy/localBusy during network wait. Existing recovery and projection gates have priority. Session/UUID/snapshot/foreground and store read revision rechecked before localBusy-protected public schedule save. Stop on error/concurrent edit/route hide; next observation retries. No automatic periodic retries or background OS service. Batch refresh after successful saves. Never create sync intents or history.
- Native bounded List directly under Refresh for show/movie progress; one LazyForEach and IDataSource per view, not nested in unbounded Scroll. Retain current page size and existing group/header order, filters, pin/hold, search, quick mark, footer paging; same identities and changed visual keys notify affected rows, membership/order change reloads. Collection/calendar/discovery remain existing bounded pagination. No automatic infinite scroll. Poster/translation fetching remains current-page-based (not true viewport-based). Native rendering and gesture behavior require device test.
- Cross-process fixtures: separate Node write/read processes using serialized cache, 393 synthetic shows, unchanged disk reuse, one changed show recompute, corrupted/mismatched scope and expiry, pending checkpoint refusal; data-source listener mocks verify unchanged, row update and reorder. Source wiring assertions for account checks and guarded directory repair. CI HAP build verifies ArkTS. These are pure-model counts, not real cold-start timings or real SQLite/TaskPool/ArkUI performance. Verify cold kill/reopen, same data and changed cloud/local state, offline fallback, logout, account switches, one mark, interrupted repair, swipe/pull refresh/pagination/collapse and poster/translation updates on device.
